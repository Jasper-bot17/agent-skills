# 会议纪要整理助手

## 一、技能定位

本技能用于将**非结构化的会议原始记录**转化为**可执行、可追溯的结构化会议纪要**。核心价值在于：

- 从散乱的速记/转写中提取真正有价值的信息
- 明确区分「讨论内容」「已决事项」「待办行动」「悬而未决」
- 为每个行动项绑定负责人和截止日期，避免会后无人跟进
- 输出格式统一，便于归档、检索和后续追踪

## 二、触发场景

当用户出现以下需求时使用本技能：

1. 用户提供了会议记录、速记、聊天截图、语音转写文本，要求整理成纪要
2. 用户说「帮我整理一下这次会议的要点」「把这段会议记录变成纪要」「生成会议纪要」
3. 用户需要从会议内容中提取 action items / 待办事项 / 决议
4. 用户需要将多轮讨论（如群聊记录）汇总成会议结论
5. 用户需要为某次会议生成可分发的正式纪要文档

## 三、输入要求

用户需要提供以下信息（部分可由 AI 从文本中推断，缺失时主动询问）：

| 输入项 | 是否必需 | 说明 |
|---|---|---|
| 会议原始文本 | 必需 | 速记、转写、聊天记录等 |
| 会议主题/标题 | 建议 | 未提供时从内容推断 |
| 会议日期 | 建议 | 未提供时标注「日期待补」 |
| 参会人员 | 建议 | 未提供时从文本中提及的人名提取 |
| 输出格式 | 可选 | 默认 Markdown；可选 Word/飞书文档 |
| 语言 | 可选 | 默认与输入语言一致 |

## 四、操作步骤

### 步骤 1：读取并理解原始记录

1. 完整读取用户提供的会议文本（文件、粘贴文本、截图 OCR 结果等）
2. 如果文本过长，分段读取，确保不遗漏关键信息
3. 识别会议的基本脉络：开场 → 议题讨论 → 决议 → 收尾

### 步骤 2：信息分类提取

将原始内容按以下维度分类提取：

#### 2.1 会议元信息
- 会议主题
- 会议时间
- 参会人员（主持人、记录人、出席者、缺席者）
- 会议类型（周会/评审/讨论/汇报等）

#### 2.2 关键讨论点
按议题分组，每个议题包含：
- 议题名称
- 核心观点（不同立场/方案）
- 讨论要点（数据、依据、风险）
- 结论倾向

#### 2.3 已决事项（Resolutions）
明确标注「已决定」「确认」「通过」「就这么定」等表述对应的结论。
每条决议包含：决议内容、决策依据（如有）。

#### 2.4 行动项（Action Items）
从「需要做」「谁来做」「什么时候完成」等表述中提取。
每条行动项必须包含：
- 任务描述（做什么）
- 负责人（谁来做）— 无法确定时标注「待指定」
- 截止日期（什么时候完成）— 无法确定时标注「待确认」
- 优先级（高/中/低）— 根据语境判断
- 关联决议（如有）

#### 2.5 待决问题（Open Questions）
记录「还需要讨论」「待定」「下次再说」「需要进一步确认」等未闭环事项。

#### 2.6 下次会议议题
从「下次讨论」「下周跟进」等表述中提取。

### 步骤 3：使用辅助脚本提取行动项（可选）

对于较长的文本，可以使用 `scripts/extract_actions.py` 进行初步的行动项模式匹配，辅助人工/AI 复核：

```bash
python3 scripts/extract_actions.py <input_file> [--output <output_file>]
```

脚本会基于关键词模式（如「负责」「跟进」「完成」「截止」「deadline」「action」等）标记候选行动项，输出 JSON 格式供后续整理。**注意：脚本结果仅作辅助，必须经过 AI 语义复核后才能写入最终纪要。**

### 步骤 4：生成结构化纪要

使用 `templates/minutes-template.md` 作为输出模板，将提取的信息填入对应章节。

输出结构如下：

```
# {会议主题} - 会议纪要

## 基本信息
- 会议时间：
- 会议地点/形式：
- 主持人：
- 记录人：
- 参会人员：
- 缺席人员：

## 一、会议议程
1. ...

## 二、关键讨论
### 议题 1：{名称}
- 背景：
- 讨论要点：
- 结论：

## 三、已决事项
| 编号 | 决议内容 | 备注 |
|---|---|---|

## 四、行动项
| 编号 | 任务 | 负责人 | 截止日期 | 优先级 | 状态 |
|---|---|---|---|---|---|

## 五、待决问题
| 编号 | 问题 | 负责人 | 预计解决时间 |
|---|---|---|---|

## 六、下次会议
- 时间：
- 议题：
- 准备事项：

## 附录：原始记录摘要
（可选，保留关键原文片段供追溯）
```

### 步骤 5：质量自检

生成纪要后，逐项检查：

- [ ] 行动项是否都有负责人？没有的标注「待指定」
- [ ] 行动项是否都有截止日期？没有的标注「待确认」
- [ ] 已决事项与行动项是否区分清楚？（决议是「定了什么」，行动项是「要做什么」）
- [ ] 是否遗漏了重要讨论点？
- [ ] 待决问题是否都记录了？
- [ ] 人名、日期、数字是否与原文一致？
- [ ] 纪要语言是否简洁、客观、无歧义？

### 步骤 6：交付与后续

1. 将纪要以 Markdown 格式输出给用户
2. 如用户需要，可转换为 Word（.docx）或创建飞书文档
3. 提醒用户：行动项的负责人和截止日期如有不确定，应在会后尽快确认
4. 建议用户将纪要归档到项目文档库，并在下次会议时回顾行动项完成情况

## 五、输出规范

### 语言风格
- 客观、简洁、书面化
- 避免口语化表达（如「然后」「那个」「嗯」）
- 决议和行动项使用陈述句，明确无歧义
- 不添加原文中没有的主观判断

### 行动项描述规范
- 以动词开头（如「完成」「提交」「联系」「调研」「准备」）
- 包含明确的交付物（如「提交 PRD 文档」而非「搞一下 PRD」）
- 负责人使用姓名，不使用「他」「他们」「相关同学」
- 截止日期使用具体日期（如「2026-09-15」），不使用「下周」「尽快」

### 优先级判定
- **高**：阻塞其他工作、有明确外部 deadline、影响关键路径
- **中**：重要但不紧急、本迭代内需要完成
- **低**：优化类、长期改进、可延后

## 六、注意事项

1. **不编造信息**：原文中没有的人名、日期、结论不得自行补充。缺失项明确标注「待补」「待确认」。
2. **保留争议**：如果会议中存在未达成一致的分歧，应如实记录不同观点，不得单方面选择某一方作为结论。
3. **敏感信息**：如会议涉及人事、薪酬、法律等敏感内容，提醒用户注意纪要的分发范围。
4. **多语言处理**：如会议记录中混用中英文，输出时保持术语一致性，关键术语可中英对照。
5. **长文本处理**：超过 5000 字的会议记录，建议先按议题分段整理，再合并为完整纪要。
6. **行动项可执行性**：如果某个行动项过于模糊（如「优化一下体验」），在纪要中标注「需进一步拆解」，并建议会后明确具体交付物。

## 八、使用示例

### 示例 1：基础整理
**用户输入**：粘贴一段项目周会的速记文本，说「帮我整理成会议纪要」。
**处理**：按步骤 1-4 提取信息，生成结构化纪要，输出 Markdown。

### 示例 2：仅提取行动项
**用户输入**：「从这段会议记录里把所有待办事项列出来」。
**处理**：重点执行步骤 2.4，输出行动项表格，包含任务、负责人、截止日期。

### 示例 3：群聊记录整理
**用户输入**：导出的微信群聊记录（多轮对话），要求汇总讨论结论。
**处理**：先按时间线梳理讨论脉络，区分不同议题，再提取决议和行动项。

### 示例 4：生成正式文档
**用户输入**：会议记录 + 「帮我生成可以发给客户的正式纪要」。
**处理**：生成纪要后，调整语言为正式商务风格，去除内部术语，输出 Word 文档。
